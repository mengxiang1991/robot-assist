首次就绪与日常运行

  1. 准备运行环境。初始化本地存储、凭据密钥和服务账号，启动管理服务与 Worker。页面分别显示 API、数据库与 Worker 是否就绪。
  2. 配置推理与市场。填模型地址、ID 和凭据引用，测试模型能力；设置已有市场的目录入口与认证。在来源页确认访问与获取制品的权限。
  3. 装配功能。选择业务模板或新建 Flow。从市场导入 Skill/MCP，或使用已登记的 CLI。补齐本机路径、凭据、输入输出映射和权限，试跑后启用。
  4. 发布和调度。调试 Flow 后发布不可变版本。用手工运行核对结果，再创建计划，确认时区、下次触发、并发、补跑和自动授权。
  5. 处理异常。在工作台处理审批、待输入和未知结果；运行详情提供失败节点、外部编号、重新核验及允许的重试操作。

内置 Agent 如何实现

Worker 持有执行上下文和允许的工具，把当前任务、历史结果和工具 Schema 交给所选模型。模型返回最终输出、补充问题或一个工具调用建议。Worker 验证建议并执行，直到满足输出要求或达到运行预算。

阶段Worker 的行为持久化记录
创建解析默认模型与工具版本，锁定 Flow、执行策略与业务输入运行快照保存最终解析出的版本、参数和触发基准
推理检查时间、Token 与步数预算，按模型能力选择结构化输出或工具调用调用耗时、用量、模型标识和脱敏结果
工具决策核验工具在当前 Flow 的白名单、输入类型、操作权限和输出边界调用参数摘要、节点执行 ID、审批状态
暂停与续跑缺输入或需审批时存检查点、释放 Worker；恢复时核验身份、参数摘要和剩余预算检查点、审批记录、已经完成的工具调用
结束校验输出 Schema；遇到超预算、取消或不明确的外部写结果时记录相应状态业务结果、外部编号、终止原因与事件

会议室首期使用确定性 Flow，将模型限制在结构化解析节点。以后可以在同一 Flow 加 Agent 节点，例如在多个只读工具之间选择检索路径。所有节点共用同一权限检查和结果记录。

统一配置、版本与状态

资源保存与发布变更影响
模型配置名称、提供方、地址、模型 ID、能力与凭据引用。保存后可连接测试，再设为默认。默认值变化影响以后新运行。正在运行的任务使用快照中的模型配置版本。
市场来源服务地址、认证引用、目录及制品获取适配。测试分别返回目录和下载状态。停用后停止新的发现和导入。已安装版本仍按本机状态提供。
工具版本记录来源、版本、摘要、操作 Schema、读写性质、依赖与权限。测试通过后启用。版本升级并行安装。管理员可紧急禁用，执行器在新调用前重新检查权限。
Flow 与模板草稿可编辑；发布固定输入输出、节点图、工具与策略引用。计划选择具体发布版本。复制模板生成独立草稿，可更新或回滚到已有版本。
定时计划保存 Flow 版本、输入、触发时间、时区、授权范围、补跑与并发策略。暂停仅阻止未来触发。已入队运行单独取消。批量子项各有记录。

凭据值单独加密，由配置引用解析。运行快照不包含明文凭据。凭据轮换后按引用取当前有效密钥，审计记录引用与密钥版本。

服务接口与实现顺序

资源建议接口后端职责
模型GET /models · POST /models · POST /models/{id}/test保存配置引用，异步探测服务能力
市场GET /market/sources/{id}/items · GET /market/items/{id}/versions · POST /market/imports适配市场接口。版本导入为异步任务，返回任务 ID 和状态
工具GET /tools · POST /tools/{id}/probe · POST /tool-versions/{id}/enable验证运行环境、发现 MCP 工具、启用明确版本
模板和 FlowGET /templates · POST /workflows · POST /workflows/{id}/validate · POST /workflows/{id}/publish实例化模板，校验节点图与引用，固定版本
运行和调度POST /runs · GET /runs/{id}/events · POST /schedules/preview事务入队、任务状态反馈、触发时间预览及控制

建议资源统一挂在 /api/v1 下。实现顺序为基础存储和任务队列 → 模型与 Worker → 市场和工具 → Flow 和调度 → 首个业务模板 → 扩展验证。市场接口与会议室 Skill 的实际能力需对照现有系统确认，两个适配器可以先用测试替身验证平台闭环。

发布验收

  • 干净环境部署后，通过 Web 配置模型；从市场导入指定版本的 Skill 和 MCP，并能分别验证运行环境和工具发现。
  • 通过 CLI 节点传入受约束参数并解析输出；通过 Agent 节点使用已授权工具，调试记录能解释为什么结束或暂停。
  • 会议室模板完成手工、定时、批量预订；重复触发、外部超时、换版本及关闭计划都有可复现的结果。
  • 新增知识库摘要时复用配置中心、Flow、调度和运行记录；Docker 与虚机都能恢复备份并启动。

模板清单示例 · 知识库周摘要

id: knowledge-weekly-digest
version: 1
title: 知识库周摘要
input_schema: input.schema.json
result_schema: digest.schema.json
workflow: flow.json
tool_dependencies:
  - slot: knowledge_lookup
    kind: mcp
    capability: search_docs
    effect: read
configuration:
  model_ref: default
  result_view: markdown
triggers: [manual, schedule]
  1. 从市场导入知识库 MCP，探测并选择已允许的文档查询操作。
  2. 复制摘要模板，填写查询范围、关键词、每周时间区间与输出要求，并将工具绑定到查询槽位。
  3. 顺序执行「查询文档 → 模型摘要 → 保存结果」。模型结构化输出标题、要点与来源列表。
  4. 手工试跑，核对来源与空结果。发布后可设为每周五运行；Hook 上线后订阅摘要完成事件。

现有 MCP 和通用 Markdown 结果组件满足要求时，新增模板文件即可。若需要知识来源筛选组件，再注册该模板专用页面。

模板发现、校验与升级

  1. 系统启动时登记内置模板清单。模板 ID 全局唯一，版本不可覆盖，清单声明所需节点类型和工具槽位。
  2. 用户从功能库实例化后得到 Flow 草稿。发布校验图、Schema、工具版本、权限、凭据引用及副作用策略。未绑定必需槽位时，页面指出缺失项。
  3. 新增版本可在同一环境并行测试。已有运行保留旧版本快照，计划切换前展示参数和权限变化。
  4. 用契约测试覆盖工具输入输出，用一条端到端用例覆盖创建、运行和结果展示。测试时将模型、市场及工具替换为可控服务。

会议室预订计划

演示为每天触发；正式版支持每周、指定日期和 Cron，并预览下次触发时间。

每个日期生成独立子任务；日期覆盖提示词中的相对日期，时间和房间条件沿用提示词。

预订的关键规则

  • 以实际触发时间与配置时区解析“下周一”，同时保存解析基准。
  • 缺少日期、时长或关键条件时进入待补充状态，不猜测提交。
  • 正式提交前再次校验可用性；冲突时按明确的备选规则处理。
  • 同一计划、目标时段和资源使用幂等键，防止重复预订。
  • 写操作超时后先查询结果；无法确认则标记“待确认”，不盲目重试。
  • 批量任务独立记录结果，仅重试明确失败的子任务。

调度语义

  • 计划与执行实例分离，启停不删除历史记录。
  • 调度器事务写入触发记录和任务；唯一键避免重启重复入队。
  • 默认错过触发直接跳过，可配置补跑一次及过期窗口。
  • 默认同计划不重叠；支持排队或跳过，限制批量并发。
  • 保存 IANA 时区；夏令时重复时段默认只执行一次。

执行与恢复

  • Worker 领取任务后持有租约并发送心跳。
  • 进程崩溃后回收过期租约；写操作先核对外部结果。
  • 节点级超时、退避重试、最大步数和 Token 预算。
  • 运行固定引用工作流、提示词和 Skill 版本。
  • 取消停止后续节点；已完成外部预订需另行取消操作。

  • 连接测试、超时与预算
  • 任务级模型覆盖

部署方案

Docker Compose：api + worker 两个容器，共享本机数据卷；首期单 Worker，通过数据库事务领取任务。SQLite 放本地磁盘，不放网络文件系统。

轻量虚机：同一发布包，systemd 分别托管 API 与 Worker；无需容器也能运行。

资源估算：外部模型 API 场景可从 1–2 vCPU / 1–2 GB 内存起步，需压测验证；浏览器自动化和本地模型另计。

扩容路径：数据库切换 PostgreSQL，再按吞吐引入消息队列和多 Worker，保留工作流与工具协议。

运行边界

  • 默认仅本机或内网访问，远程访问配置 TLS 和登录鉴权。
  • 执行器非 root，限制目录、网络、进程时间与资源。
  • 不挂载 Docker socket；不把模型输出直接拼接成 shell。
  • API 和调度不能依赖网页持续打开。
  • 数据库一致性备份、配置导出和恢复演练。
  • 健康检查与磁盘、任务积压、失败率监控。

核心数据与接口

WorkflowVersion → Schedule → Run → StepRun；另设 Tool、CredentialRef、BookingItem、EventOutbox。

计划保存时区、触发规则、启停与补跑策略；运行保存版本快照、幂等键、租约、状态与错误；预订项保存外部编号及确认状态。

POST /runs 手工触发 · POST /runs/preview 参数预览 · POST /runs/{id}/approve 确认执行 · PATCH /schedules/{id} 更新计划 · GET /runs/{id} 查看进度

任务结果和事件 Outbox 同事务写入；消息派发为至少一次投递，接收端通过 event_id 去重。

旅程 04 · 批量预订与部分失败

选日期或粘贴日期列表 → 去重与检查 → 生成逐项预览 → 确认批次 → 分项执行 → 查看汇总。输入错误定位具体行；提交前显示有效项、无效项与总量，不静默丢弃错误日期。

结果用户看到什么允许的操作
成功房间、时段、外部编号查看；若工具支持可发起取消工作流
明确失败无房 / 凭据过期 / 参数不合法修正后重试此项，保持原始记录

旅程 05 · 定时失败后的处理

收到失败事件 → 打开运行详情 → 定位失败节点 → 修复凭据或参数 → 创建关联重试运行 → 确认结果。错误提示同时提供原因、影响范围和可执行动作。

凭据失效可暂停相关计划；消息推送失败只影响通知，不把已经成功的预订改成失败。

工具接入与工作流使用

路径：产品 UI 原型 → 配置中心 → 选择工具类型 → 填写并校验 → 在 Worker 环境测试 → 启用 → 绑定 Flow → 手工试运行 → 按需配置定时计划。

模型与内置 Agent · 首次配置

  1. 打开「配置中心 → 模型」，填写 API 类型、Base URL、模型 ID、凭据引用与超时，保存为默认模型。正式应用由 Worker 测试连接及任务所需的结构化输出或工具调用能力。
  2. 打开 Flow 并选择执行方式。会议室模板使用固定工作流，模型负责提取预订条件，Worker 按节点执行。开放式任务可选择内置 Agent，由 Worker 运行模型和工具调用循环，执行工具权限、步数上限及审批规则。

Agent 执行器属于应用。模型提供推理，可以部署在外部或本地。Skill、MCP 和 CLI 提供任务工具；市场负责提供 Skill 包和 MCP 服务定义。

市场接入旅程 · 从发现到启用

  1. 连接自己的市场。在「配置中心 → 市场来源」填写名称、服务地址和认证引用。Worker 与市场可能处在不同网络，分别检查目录访问、包下载和运行所需的网络。
  2. 找条目、选版本。按 Skill / MCP 分类检索。详情显示发布者、版本、运行依赖、权限、安装方式和版本信息。用户选定版本后生成草稿。
  3. 导入。Skill 下载指定版本的包，检查摘要与目录结构，存到 Worker 可读的版本目录。MCP HTTP 条目导入端点与协议配置。MCP stdio 条目导入运行清单，运行器或安装包按市场提供的方式准备。
  4. 补齐本机配置。填写凭据引用、确认网络与目录访问范围，交由 Worker 做只读探测或工具发现。探测通过后启用并绑定 Flow，先手工试看结果，再设置定时。
  5. 更新。新版并行导入、测试并发布为新工具版本；已有 Flow 和定时计划继续引用原版本，直至显式切换。市场暂不可达时保留已经安装的 Skill 和已保存的 MCP 配置。远程 MCP 的在线状态独立检查。
接入边界设计契约
市场来源配置名称、目录地址、认证引用、支持类型、连接测试；按实际市场接口实现适配。
目录与版本CatalogPort.search(kind, query)、get_version(item_id, version)。返回发布者、版本、摘要、权限和获取方式。
导入记录保存 source_id、item_id、version、digest（制品可用时）、本机配置与验证结果。状态：草稿 → 获取中 → 待配置 → 待测试 → 已启用；失败显示原因和重试入口。
获取与校验制品下载到暂存区。校验通过后再发布到版本目录。远程端点保存来源信息及工具发现时观察到的输入契约。

市场 API、认证方式和制品格式按你现有市场的接口确定。CLI 继续通过本机登记接入。

旅程 07 · 导入现有会议室 Skill

  1. 在市场选择现有会议室 Skill 的版本导入，或在配置中心手工登记。确认名称、Worker 可读的目录、运行适配方式、版本和凭据引用。若采用 Agent Skills 目录格式，系统读取 SKILL.md，展示描述和可用资源。Agent Skills 规范
  2. 根据实际 Skill 映射可用操作、输入字段与结果，例如将候选查询和提交分开。Worker 检查文件权限、运行时依赖与账号，优先使用只读查询测试。
  3. 创建会议室 Flow，绑定 Skill 版本。将日期、时段、人数和设备映射到查询节点，将选中的房间和确认结果传给提交节点。
  4. 手工运行时先核对候选与审批；定时自动提交须满足计划授权范围。缺文件时查 Worker 的挂载路径，凭据失效时更新引用，提交超时后先核验外部结果。

旅程 08 · 连接 MCP 服务

  1. 从市场导入服务定义或手工添加。Streamable HTTP 需核对端点和认证引用，stdio 需确认 Worker 内的可执行文件、独立参数和环境变量引用。MCP 传输规范
  2. 从 Worker 发起连接测试，展示连接和工具发现结果。选择允许使用的工具，核对输入格式、访问范围和副作用。
  3. 在 Flow 添加 MCP 工具节点，选择已启用服务及工具，例如「知识库 → 查询文档」，把上一步的关键词映射到工具输入。先手工运行，核对输出和错误记录，再启用定时计划。
  4. HTTP 连接失败时检查地址、网络和认证；stdio 失败时检查 Worker 内的路径、权限和依赖。工具消失或输入格式变化时重新发现、检查映射并发布新 Flow 版本。

旅程 09 · 登记并调用 CLI

  1. 填写 Worker 内的绝对可执行路径、固定子命令、允许的参数、工作目录和超时。真实运行使用参数数组，按类型填充参数。
  2. 使用版本探测或只读样例测试，检查退出码和输出。预先约定输出格式，例如 JSON；失败日志保留退出码及脱敏错误摘要。
  3. 在 Flow 选择已登记的 CLI，例如「报告生成 → 生成摘要」，将前序节点的产物 ID 映射到明确的参数。Worker 校验该产物路径后执行，将 JSON 输出传给下一节点。
  4. 工具缺失时补齐镜像或虚机依赖；参数错误时修订映射；输出格式变化时重新验证。写入文件的节点需限定可写目录。

旅程 10 · 从配置到发布 Flow

新增草稿 → 选择触发方式 → 添加模型或工具节点 → 映射输入与输出 → 设置审批及失败分支 → 用样例执行 → 发布版本 → 建立定时计划。

以会议室为例，Flow 保存「怎么执行」，计划保存「什么时候执行、传什么参数」。修改工具版本或节点映射时发布新 Flow 版本，计划再选择是否切换。

通用交互标准

  • 时间显示绝对日期和时区，悬停可显示 UTC。
  • 危险操作显示影响范围；启停是可逆操作。
  • 提交按钮防连点，后端仍需幂等保护。
  • 表单离开前提示未保存修改。
  • 键盘可操作，状态不只依赖颜色。
  • 窄屏侧栏折叠，表格可横向滚动。

错误提示应该能指导行动

不采用：“任务失败，错误 500”。

建议：“会议室凭据已过期，本次尚未提交。更新凭据后可重新运行。”

结果未知：“请求已发出，但未收到确认。请先查询结果，避免重复预订。”

每条错误携带 error_code、request_id、可重试标记及下一步动作。

class ToolPort(Protocol):
    async def describe(self) -> ToolManifest: ...
    async def invoke(self, request: ToolRequest) -> ToolResult: ...

class ToolRequest:
    tool_version: str
    arguments: dict
    run_id: str
    step_id: str
    idempotency_key: str
    credential_ref: str
    deadline: datetime

class ToolResult:
    status: Literal['succeeded', 'failed', 'unknown']
    output: dict
    external_reference: str | None
    error_code: str | None

class ModelPort(Protocol):
    async def generate_structured(
        self, messages, schema, budget
    ) -> ModelResult: ...

适配器负责协议与结果归一化；权限、预算和审计由运行时统一执行。idempotency_key 传入工具不意味着外部系统一定支持幂等，必须在能力清单中声明支持程度。

SOFTWARE ARCHITECTURE

代码架构：核心规则不依赖具体工具

采用模块化单体与端口适配器思路；先解决职责和状态，再根据真实负载拆服务。

依赖方向与模块职责

入口层HTTP / 调度 / Worker CLI
验证身份与格式，调用用例
应用层创建运行 / 审批 / 发布
事务、授权、协调领域对象
领域层Run / Schedule / Policy
状态迁移、幂等、业务约束
端口 ← 适配器数据库 / 模型 / 工具
通过依赖注入接入核心

核心 domain 不导入 FastAPI、数据库驱动或模型 SDK；application 依赖 domain 和 ports；adapters 实现 ports；entrypoints 负责装配。禁止 booking 模块直接操作调度器内存或绕过 ToolPort 执行命令。

两类执行模式共用运行底座

模式适用边界
确定性工作流会议室预订、定时批处理节点和分支可预测；AI 只负责指定节点的理解或转换
受约束 Agent需要多轮检索、工具选择的开放任务工具白名单、最大轮数、预算、超时、写操作审批

Agent 节点内部可以“模型 → 工具 → 模型”循环，但不能绕过权限守卫。首期预订优先用确定性工作流，避免让模型自由决定重复提交或更改会议时段。

关键执行时序

用户 → API：POST /runs/preview（提示词、模板版本）
API → DB：创建 preview 运行，保存输入及解析基准
Worker → 模型：解析结构化意图
Worker → Policy：校验参数、工具权限与预算
Worker → Skill：只读查询候选房间
Worker → DB：保存预览快照，状态 awaiting_approval
API → 用户：返回候选、最终参数摘要与预览版本
用户 → API：POST /runs/{id}/approve（预览版本）
API → DB：原子校验版本、有效期、当前状态，入队
Worker → Skill：再次查询可用性，提交预订
Worker → Skill：核验外部编号与目标时段
Worker → DB：结果 + 状态 + Outbox 事件同事务提交
Dispatcher → Hook：异步推送，记录投递尝试

若确认过期或资源变化，返回冲突并重新预览。自动计划在策略允许范围内跳过人工确认；不跳过参数和权限校验。

运行状态机

queued → running
running → awaiting_input → queued
running → awaiting_approval → queued
running → succeeded
running → failed
running → unknown → succeeded / failed
running → cancel_requested → cancelled
queued  → cancelled

批次汇总：
全部成功 → succeeded
成功与失败混合 → partial_success
存在未确认项 → needs_attention

审批和补充输入不占用 Worker；恢复后从检查点继续。未知状态不是失败；只有核验结果后才能决定后续动作。

权限与策略守卫

输入 → Schema 校验
     → 用户与工具授权
     → 允许的房间、时段、数量
     → 凭据引用解析
     → 超时、预算与并发检查
     → 调用适配器
     → 结果归一化与审计

审批策略固定在运行快照中；紧急禁用工具是实时生效的全局限制。工具返回文本当作数据，不能覆盖系统权限或自动获得执行资格。

API 契约与错误语义

接口语义主要返回

把设计变成可验收的开发任务

工作包交付内容验收条件

用户双击提交，或网络重试相同请求返回同一个运行，不生成第二个有效提交
Worker 在提交后、写入结果前崩溃通过外部查询恢复，或进入结果未知
API 在调度事务中重启事务回滚或完整提交；同一触发时刻最多一个入队实例
暂停计划与到期扫描同时发生事务内校验当前启用状态；已创建实例明确可见
审批时预览版本已改变返回冲突，要求重新确认最新参数
批量 20 项中 3 项失败、1 项未知逐项显示，失败可重试，未知需核验，成功项不重跑
工具输出包含指令或伪造授权当作数据处理，不修改执行权限
Hook 连续返回错误按策略重试后进入死信；任务结果保持不变
数据库备份恢复到新机器迁移版本可识别，主密钥可用；恢复后计划先暂停并核验外部状态

运维与可观测性

  • 日志关联 request_id、run_id、step_id、attempt。
  • 观察排队时长、节点耗时、失败分类、未知结果数。
  • 模型记录 Token 用量；费用仅在配置价格时估算。
  • 存储保留策略可配置；删除日志不删除必需审计与外部编号。
  • 升级前备份；数据库迁移不假设自动可逆。
  • 恢复演练时禁用调度和通知，核对完成后再启用。

首期明确不做的内容

  • 多租户计费、复杂组织权限与公开市场。
  • 自建模型训练或本地模型集群调度。
  • 任意代码执行平台和无限制 Agent。
  • 跨多个预订的强事务承诺。
  • 首期就引入 Kubernetes、分布式锁服务与复杂消息系统。

这些边界用于控制开发规模；代码接口保留扩展能力。

架构决策记录

决策理由重新评估条件
模块化单体部署简单，统一事务，便于个人维护独立扩容或故障隔离有明确需求
SQLite 起步零数据库服务配置，支持轻量本机部署多机 Worker、写竞争、数据规模持续增长
API 与 Worker 分进程工具阻塞不会拖住管理页面继续保留边界，可独立扩展 Worker
不可变工作流版本运行可复现，计划行为可解释不撤销；新增迁移和兼容策略
Outbox 预留业务结果与通知事件不丢关联接入外部消息系统后仍保留事务边界
